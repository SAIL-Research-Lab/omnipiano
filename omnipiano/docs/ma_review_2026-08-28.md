## 1. 🆕 N1:`ray.init(local_mode=True)` 在 pin 的 ray 版本上直接崩溃

**位置**
- `omnipiano/multiagent/_train_ippo.py:530` — `ray.init(local_mode=(args.num_workers == 0), ...)`
- `omnipiano/multiagent/_rllib_smoke.py:101` — `ray.init(local_mode=True, ...)`

**现象**
`setup.py` 的 `marl` extra pin 了 `ray[rllib]==2.55.1`,而这个版本已经移除 `local_mode`:

```
RuntimeError: `local_mode` is no longer supported. For interactive debugging consider using the Ray distributed debugger.
```

所以 `--smoke-test`(内部把 `num_workers` 置 0)和任何 `--num-workers 0` 的调用都在训练开始前就崩;`_rllib_smoke.py` 同样。默认的 `--num-workers 4` 路径不受影响(`local_mode=False`)。

**为什么测试没抓到**
`test_ippo_infrastructure.py` 全是 mock(`_FakeAlgorithm` 等),不启动真 Ray。建议至少在 CI 之外保留一条真实 `--smoke-test` 作为手动验证步骤。

**修复**
删掉 `local_mode` 参数即可,`num_workers=0` 时 RLlib 会在 driver 进程里采样,语义等价:

```python
ray.init(ignore_reinit_error=True, log_to_driver=False)
```

## 2. #1:`omnipiano.make_parallel` 没有从顶层导出

**位置**
`omnipiano/__init__.py` 只有 `from omnipiano.envs.registration import make, register`,没有导出 `make_parallel`。

**为什么是问题**
代码和文档到处承诺这个入口存在:
- SA `make()` 收到 `-MA-` id 时的报错文本(`omnipiano/envs/registration.py:257`):`use omnipiano.make_parallel(...) instead`;
- `make_parallel` 收到 SA id 时反向提示 `Use omnipiano.make(...)`;
- `multi_agent_design.md` 所有用法示例都写 `omnipiano.make_parallel(...)`(§4 决策:SA/MA 是两个平行入口,gymnasium.Env vs PettingZoo ParallelEnv)。

用户照报错提示写 `omnipiano.make_parallel(env_id)` 会得到 `AttributeError: module 'omnipiano' has no attribute 'make_parallel'`。目前唯一能用的写法是 `from omnipiano.multiagent import make_parallel`(训练脚本用的就是这个,所以没撞上)。

**修复**(一行,注意放在 `from omnipiano import envs` 之后,否则循环导入——`omnipiano.multiagent` 依赖 SA registry):

```python
# omnipiano/__init__.py
from omnipiano.envs.registration import make, register  # noqa: E402
from omnipiano import envs  # noqa: E402, F401
from omnipiano.multiagent import make_parallel  # noqa: E402
```

并在 `__all__`(如有)里加上。

## 5. #4:`reset(seed=X)` 同 seed 不重建

**位置** `omnipiano/multiagent/parallel_env.py:182-190`

```python
if seed is not None and seed != self._current_seed:   # ← 多了 seed != … 这个条件
    self._env = self._env_builder(seed)
    self._current_seed = seed
ts = self._env.reset()
```

**背景:`_env.reset()` 和重建是两个层次**
- `_env.reset()` 只是开新 episode(手回初始位、MIDI 回第 0 拍),**不重置 RNG**。dm_env 链里有两个 RNG 在构建时用 seed 初始化、之后每 step 前进、永不倒带:`composer.Environment._random_state`(初始手位、apply_action 等所有 task 随机性都从它拿)和 `DmEnvObsNoiseWrapper._rng`(obs 噪声)。
- 重建整条链是把它们倒回起点的唯一方式。

**问题**
Gymnasium / PettingZoo 合同:`reset(seed=42)` 每次都必须从 seed 42 的第 0 个随机数开始,连续两次 `reset(seed=42)` 要得到逐位相同的 episode。MA 现在只在 seed 变化时重建:

```
env = make_parallel(id, seed=42)   # 构建,RNG 在位置 0
env.reset(seed=42)                 # seed 没变 → 不重建 → episode 1 用 RNG 位置 0..N
env.reset(seed=42)                 # seed 没变 → 不重建 → episode 2 用 RNG 位置 N..2N   ✗
```

SA adapter(`omnipiano/envs/dm_env_adapter.py:119-138`)是 `if seed is not None: 重建`,不管 seed 是否相同,并在注释里写明了上述理由。

**为什么现在看不出来**
当前 MA env 都是 clean env,链里没有 obs-noise wrapper,composer 的 `_random_state` 也没被任何随机初始化用到,所以两个 episode 恰好逐位相同(7 月实测过)。这是巧合不是正确:一旦注册 obs-noise 的 MA env(`make_parallel` 的 guard 是放行 obs 通道的),"确定性 eval"就会不确定。

**成本评估:不影响训练**
- 实测重建 ~0.9s。
- 训练:RLlib 只在每个 worker 首次 reset 传 seed,之后都是 `seed=None` → 全程每 worker 只重建 1 次。
- 评估:`evaluate_ippo` 每集用不同 seed(`eval_seed + i*10_000`,与 SA 模板一致),本来就每集重建;改动零增量。

**修复**(对齐 SA,去掉一个条件即可):

```python
if seed is not None:
    self._env = self._env_builder(seed)
    self._current_seed = seed
```

原地 reseed 两个 RNG 技术上可行(composer 有公开 `random_state` 属性;`DmEnvObsNoiseWrapper` 是我们的代码),但目前没有收益,且会让 SA/MA seed 语义再度分叉,暂不做。

## 7. #6:MA chain builder 是 SA `_build_dm_env_chain` 的复制品,已漂移 — **请先研究,再讨论,暂不改**

### 7.1 背景:一个 OmniPiano env 是怎么搭出来的

SA 的 `omnipiano.make()`(`omnipiano/envs/registration.py`)分两层:

1. **dm_env 层**(`_build_dm_env_chain`, 第 404 行起)
   `PianoTask → EpisodeStatistics → [PianoSoundVideo] → MidiEvaluation → [DmEnvObsNoise] → [ObservationActionReward] → ConcatObservation → [FrameStacking] → CanonicalSpec → SinglePrecision`
2. **gym 层**(第 488 行起)
   `DmEnvToGymnasium → MetricsWrapper → SafetyWrapper(算 cost) → RobustWrapper(action / reward 噪声) → [eval 模式 CSV logger]`

MA 的 `make_parallel` 需要同一条 dm_env 链,只是不要 `ConcatObservation`(要保留 Dict obs 才能按 agent 切片)。当初的实现方式是**把 `_build_dm_env_chain` 整段复制到 `omnipiano/multiagent/registration.py:265`(`_build_ma_dm_env_chain`),删掉 Concat 一行**;gym 层完全没有,PettingZoo env 直接包在 dm_env 上。

### 7.2 已确认的漂移

| 差异 | SA `omnipiano/envs/registration.py` | MA `omnipiano/multiagent/registration.py` | 后果 |
|---|---|---|---|
| robust 配置 | 用 `effective_robust_config`(第 347 行):`mode="eval"` 时按 `eval_noise_scale` 缩放所有噪声参数 | 直接传原始 `robust_config`,没有 `mode` / `eval_noise_scale` 概念 | MA 的 obs-noise env 永远是 train 模式噪声,无法执行 robust 分支的 matched-eval / noise-scale 扫描协议 |
| gym 层 wrapper | `MetricsWrapper` + `SafetyWrapper` + `RobustWrapper` | 无 | safety 的 cost 永远算不出来;action/reward 噪声永远注入不了。**并且是静默的**:env 能建、能训练,只是数据是错的 |
| `frame_stack` | Concat 之后再 stack,flatten 成一个向量 | 保留了 `FrameStackingWrapper(flatten=True)`,但 obs 仍是 Dict | `frame_stack>1` 在 MA 下行为未定义;`parallel_env.py` 的切片逻辑不认识 stack 后的 obs |

### 7.3 现在唯一的防线:fail-fast guard

`make_parallel` 里(`multiagent/registration.py:148-171`,2026-07-21 加入):若底层 SA env 带 `safety_config.constraints`,或 robust 的 `action`/`reward` 通道激活,直接 `ValueError` 拒绝构建。它只是**把"静默出错"变成"显式报错"**,并没有让 MA 支持这些功能。obs 通道放行,因为 `DmEnvObsNoiseWrapper` 在 dm_env 层、MA 链里确实有——但如上表,没有 eval-scale 语义。

### 7.4 为什么这是 safety / robust 兼容的前置条件(隐患)

- **保持复制品结构的代价**:将来给 MA 加 safety,就得再复制一份 `SafetyWrapper` 逻辑到 PettingZoo 层;加 robust,又得复制 `effective_robust_config` 缩放 + `RobustWrapper`。每加一样,SA 和 MA 就多一处必须手动同步的地方,而 7.2 的漂移历史已经证明这种同步不会自然发生。
- **静默错误的风险**:guard 现在只覆盖 safety constraints 和 action/reward 通道。任何未来加到 SA 链上的新 wrapper / 新配置字段(例如 `mode`、新的噪声分布、新的 metrics 键)都不会自动进入 MA,也不会被 guard 拦下——会以"MA 能跑但数据口径和 SA 不一致"的形式出现在论文数据里。
- **N-hand safety 本身还有独立设计问题**:`constraints.py` 目前是 2-hand-only(N-hand 上 cost 静默错误),这是 safety 落地时另一个要解决的问题,与本条并列而非包含。

### 7.5 一个候选方案(供讨论,不是决定)

1. 把 `_build_dm_env_chain` 提到模块级、可从 `omnipiano.envs.registration` 导入,加参数 `concat_obs: bool`;`make()` 传 `True`,`make_parallel` 传 `False`,MA 侧删除复制品。
2. 把 `mode` / `eval_noise_scale` → `effective_robust_config` 的计算抽成小函数,`make_parallel` 复用,让 obs-noise MA env 立刻获得 eval 语义。
3. `frame_stack>1` 在 MA 下显式 `raise NotImplementedError`,不留假支持。
4. guard 保留;等 gym 层 Safety/Robust 在 MA 有等价物后逐条放开。
5. 按仓库惯例,替换/绕过既有构建路径时补一个等价性 smoke test:同 seed 下 SA 链与 MA 链(concat 前)的 obs/reward 逐位一致。

做完这一步,后续 safety/robust 的 MA 工作范围就收敛到"`parallel_env.step` 里 cost / 噪声如何按 agent 分发"这一个真正的设计问题,不再碰构建链。

**请先阅读 7.1–7.4、对照两份 chain builder 的源码,之后我们一起讨论方案再动手。**

## 8. 面向未来 safety / robust 兼容的其他备注(不需要现在改)

- `_ippo_common._numeric_metrics` 会自动收集 `_global_` 里任何 `episode_*` 数值键,所以将来加 `episode_cost` 之类的指标对 eval 侧是 additive 的,不用改。
- `shared_team_reward` 硬断言各 agent reward 相等;将来若有 per-agent reward mode,需要按 `reward_mode` 分支。
- cost 通道目前在 `parallel_env.step` 没有出口;一个自然的约定是 `infos[agent]["cost"]`(per-agent)+ `_global_["episode_cost"]`。
- SA eval seed = `seed + n_envs + 1`,MA eval seed = `seed + 10_000`,基值不同但都写入 `run_config.json`;per-episode 派生规则相同。
